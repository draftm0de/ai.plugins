# plugin-create

Read `../_shared/WORKFLOWS.md` and follow **plugin-create**. Use the user project or explicit target, never this installation. Reuse known inputs; clarify only missing or contradictory facts.

Choose `--skeleton` to create a nonfunctional scaffold before domain requirements exist, or `--source` for a confirmed existing skill. Never combine them. Reuse known project/origin facts; clarify marketplace, technical name, display name, publisher and language policy only when missing or conflicting. A skeleton records pending requirements in SCOPE.md and supplies shared development instructions; do not invent domain code, capabilities or license terms. Report that implementation and acceptance remain pending.

Before asking setup questions, use the language of the user's current natural-language message. For a bare slash command, retain the established conversation language; if neither provides a language, ask briefly which conversation language to use. Do not infer it from English skill instructions, technical identifiers, neighboring repositories or documentation settings. Confirm documentation languages separately when not already established.

This language gate also applies when the target already contains a plugin. With unknown conversation language, ask only the language question first; never bundle it with an existing-plugin action question. After language is known, every question, choice and explanation uses that language only (technical names remain unchanged). Inspect the target for an existing plugin before asking creation or licensing questions. If one exists, do not restart setup or create over it. Offer only “Verifizieren” and “Konfigurieren” in German, or “Verify” and “Configure” in English. Do not offer creation of another plugin or ask for another target path in this dialog. Verification is read-only; configuration concerns marketplace associations, not recreation. Do not act on an unsubmitted selection.

Use the host's available structured question tool for the guided setup (for example `AskUserQuestion` when exposed by Claude). Do not replace that interaction with a prose questionnaire. If conversation language is unknown, ask only that first, using a short bilingual question with Deutsch/English choices, and wait before asking setup questions. Continue in the selected language with small, coherent question groups within the tool's limits; skip confirmed inputs. Present source/skeleton, documentation languages and licensing as clear choices, with free-text input for names, paths and a specific license. Do not present CLI flags as the user's required input. If the structured tool is unavailable in the current host/mode, briefly explain that limitation and ask one concise question at a time in chat. Follow the staged dialogue in `../_shared/references/workflows.md`.

Before invoking creation or writing target files, resolve the licensing decision as described in `../_shared/references/workflows.md`. Reuse an existing unambiguous target license or explicit session decision; otherwise ask which license to use or whether the user explicitly wants to defer the decision. Silence is not deferral. Preserve existing license files and clarify conflicts before writes. Report any explicitly deferred license as unresolved in the completion message; do not claim licensing is complete.

Carry the decision through to files: pass `--license MIT` with confirmed `--copyright-year` and `--copyright-holder`, or a confirmed identifier with an explicit complete `--license-file`. Ask only for missing copyright facts; publisher is not automatically rights holder. Use `--license deferred` only after explicit deferral. Follow the shared workflow for existing license preservation and unsupported templates. Check the created license file, manifest metadata and localized documentation via `checks.licensing`. Do not stop at “the helper does not generate license texts”: it now creates the selected MIT license or copies the explicitly confirmed complete license file. Preserve existing prose and resolve reported documentation gaps within the creation request.

The helper fills new skeleton documentation with localized scaffold facts and reports post-write `checks` for plugin structure, marketplace structure and documentation. Inspect these results; never equate command execution or structure validity with completed creation. Preserve existing prose and resolve reported documentation issues within the authorized scope. For imported source skills, complete the documentation from source evidence and re-run trusted structural and documentation checks. In the final report, separate structure, documentation, the licensing decision and actual license files, pending domain implementation/acceptance, and tests/host checks actually run. A `needs_attention` result means creation remains incomplete; do not hide its findings. Never execute target code as part of these checks.
