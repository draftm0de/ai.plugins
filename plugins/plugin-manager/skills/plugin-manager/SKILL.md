# plugin-manager (central entry)

Specialised actions stay in their own skills; shared rules for them are in `../_shared/WORKFLOWS.md`. Helper: `../_shared/scripts/project_setup.py`; language rules: `../_shared/references/operator-language.md`, which applies only where it does not conflict with this entry. Precedence: this entry's read-only rule and flow order win. In particular its direct `--set` before continuing and its rule to ask/save a missing language even for read-only actions do not apply here. The reference still governs the tag format, never guessing a language, reuse of the saved language and independence of content languages. Resolve paths from this loaded SKILL.md; never search host caches.

## Loop

1. Determine the explicitly selected folder (user input or current project). Ask only which one if several are possible. Never the installed Manager, a marketplace repository or unrelated projects.
2. Run `python3 -B "<helper>" status --target "<folder>"` (JSON, writes nothing, needs no plugin.json, Git, origin or marketplace). Read `next`:

| `next` | Meaning | Action |
| --- | --- | --- |
| `stop` (`state: conflict`, exit 1) | technical conflict | Explain each `conflicts` path and reason; change nothing; wait. Other project content (`code: not_fresh`, `entries`) is reported, never adopted. |
| `language` | operator language missing | follow `flows/language.md` |
| `skeleton` | shared development files, ignore rule or lock evidence missing | follow `flows/skeleton.md` |
| `sync` | a managed file differs from the template, or its source was removed and its local file is changed or accepted, and needs a decision | follow `flows/sync.md` |
| `configure` | no plugin.json yet | follow `flows/configure.md` |
| `ready` | no automatic setup flow open | greet briefly, name the state (including `skeleton.different`) and wait for input |

3. Success is judged per flow, because the answers differ. `language`, `setup` and `sync`: exit 0 and `ok: true` (with `next: "status"`). Configuration (the existing generator, whose answer has `action`, `changed`, `checks` and prose `next`, but no `ok`): exit 0 **and** `checks.status == "passed"`. After each flow that succeeded in this sense, run `status` again and decide from the new answer; never jump to the next step by assumption.
4. Stop and report instead of repeating when a flow fails (`language`/`setup`/`sync`: `ok: false` or exit 1; configuration: non-zero exit or `checks.status` other than `passed`, for example `needs_attention`, reporting the failing entries under `checks`, the files actually listed in `changed` and the generator's own `next` text) (name each concrete reason in `conflicts`/`errors` and the partial changes that actually happened, such as `created.*`, `language.saved`, `gitignore.changed`, `lock.changed`; do not repeat "nothing was written" from a status check), when the person has not answered or an external prerequisite that no answer can fix is missing (state it once and wait; a missing answer or selection is first asked for in the guided dialogue of the flow, do not ask again in a loop); a cancelled or unanswered question is such a pause: respect it, do not ask again until the entry is called again, or when a flow claimed success but the next `status` shows the same `next` without progress (report the cause, do not retry).
5. Binding: read and apply `../_shared/references/operator-language.md`, in particular its section "Language of all visible text", for every visible text you write (reports, questions, choice labels, closing or next-step card fields). Manager-specific rules stay as stated here: read-only asks and saves no language (see below), the setup order with the ignore rule, on `ready` greet briefly, name the state and wait; start no verify or other action on your own, and the success and failure rules of the flows apply unchanged.
6. Never show, quote or describe the content of a managed file or of a difference: no excerpts, diffs or content summaries, not in questions, not in the final report, not for `ready`, not for accepted deviations or kept files. Name only the path and the fact (differences exist, deviation accepted, source removed, file kept or removed). Never say the project matches the template unless `matches_template` is true. `ready` is not product acceptance and never proves a successful configuration: it only means no automatic setup flow is open, and a plugin.json that exists says nothing about the generator's checks. A configuration failure or `needs_attention` already reported in this conversation stays an open, named problem even if a later `status` shows `ready`; say so when reporting, and do not store any flag for it. In a later conversation `ready` is reported the same way, with an offer to run verify for the structural checks. A deviating managed file is never overwritten automatically: it needs the person's explicit decision (`flows/sync.md`). Only an explicit `adopt` takes over the template content; `keep` makes it an `accepted` deviation (a deliberately accepted difference), which is listed but neither re-asked nor reported as matching the template, so there is no endless re-sync.

## Read-only requests

If the request is concretely read-only (for example "check", "status", "what is missing"), run exactly one `status`: ask nothing, save nothing, start no flow, and report the result with language need, skeleton need and configuration need kept separate.

## Status answer

`{"ok", "state": "plugin"|"unconfigured"|"conflict", "plugin_configured", "next": "stop"|"language"|"skeleton"|"sync"|"configure"|"ready", "language": {"operator_language", "needs_choice"}, "skeleton": {"open", "missing_files", "lock_pending", "ignore_rule_pending", "different", "accepted_deviations"}, "removals": {"auto", "decisions", "kept", "unowned", "lock_cleanup"}, "sync": {"needed", "decisions": [{"path", "reason", "source_hash", "local_hash", "accepted", "source_changed", "local_changed", "source_file", "local_file"}]}, "files", "conflicts", ...}`. `files` states: `missing`, `identical`, `accepted` (differs, but the stored source/local pair still fits), `decision_needed`, and for managed paths whose source was removed in the parent: `removed` (local absent), `auto_remove`, `removal_decision`, `removal_kept` (stored `source_hash` null, local unchanged), `unowned` (no lock evidence, never touched). `removals` lists these separately; `removals.auto` and `removals.lock_cleanup` are executed by the skeleton flow (`next: skeleton`), `removals.decisions` by the sync flow. Priority is fixed: conflict, language, skeleton, sync, configuration, ready.

## Boundaries

The skeleton is the helper's fixed list of nine managed files plus parent folders, the ignore rule and lock evidence; it contains no plugin.json or placeholder identity. Deletion is limited to a managed file whose source was removed in the parent template and for which the lock proves ownership: it is removed automatically only if the current local hash equals the stored `local_hash` and the stored `source_hash` (untouched since it matched the template); a changed or deliberately accepted local file is always asked (keep or delete), and without lock evidence nothing is ever deleted. Locally already missing owned files only lose their lock entry. After a removal only the empty parent folders of the removed file go, bottom-up with `rmdir`, and never folders still needed, the project root, `.git`, `.idea` or `.project`; foreign files are never deleted and no folder is hashed, moved or removed recursively. Extra local files stay. An existing managed file is replaced only by an explicit `adopt` decision of the person for the shown source/local pair (`flows/sync.md`); `keep`, the skeleton flow and every other flow never replace its bytes. Removal is a separate act with its own rules: only the automatic removal and the explicit `delete` decision described here delete a file. The other existing files the helper may modify are `.gitignore` (exact rule line added), `.project/operator.json` (language, written only when none is stored) and `.project/plugin.skeleton.lock.json` (schema_version 2, hash pairs per path, merged in; an older or invalid lock is rejected unchanged, never migrated). `status`, `language` and `setup` never open `.git` or `.idea` (they only verify real directories) and need no Git, origin or marketplace. Configuration uses the existing plugin-create generator with its documented prerequisites (it reads Git metadata); this entry adds no Git mutation or network action, installs nothing and executes no target code. This does not alter configure, update, verify, publish or plugin-create. Skill text does not prove host or model behavior; activation by a slash command is untested.
