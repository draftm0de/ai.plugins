# setup (`/plugin-manager:setup`)

The state-guided skill of the Plugin Manager. Follow `flows/entry.md` with `plugin = plugin-manager` (every helper call passes `--plugin plugin-manager`); the flows `language.md`, `skeleton.md` and `sync.md` live next to it, as do `flows/configure.md` (plugin or marketplace), `flows/marketplace.md` and, on request, `flows/associate.md` (the one marketplace of a plugin). Specialised actions stay in their own skills; shared rules for them are in `../_shared/WORKFLOWS.md`. Helper: `scripts/setup_state.py`; language rules: `../_shared/references/operator-language.md`, which applies only where it does not conflict with the entry flow. Precedence: the entry's read-only rule and flow order win. In particular its direct `--set` before continuing and its rule to ask/save a missing language even for read-only actions do not apply here. Resolve paths from this loaded SKILL.md; never search host caches.

Messages to the person (failures, stops, results) follow `../_shared/references/messages.md`: two short paragraphs of running text (what could not be done, because of what, what was changed; then the request with the exact way and the call to repeat), no labels, no technical terms.

## Manager-specific rules

- Never the installed Manager or unrelated projects as target. The kinds are `plugin` (a plugin repository) and `marketplace` (a marketplace checkout); the configuration flow asks which one first.
- Configuration is two steps: the existing generator (answer with `action`, `changed`, `checks` and prose `next`, but no `ok`; success means exit 0 **and** `checks.status == "passed"`) and then `record`, which writes the configuration evidence only after that success. A configuration failure is a non-zero exit or `checks.status` other than `passed`, for example `needs_attention`: report the failing entries under `checks`, the files actually listed in `changed` and the generator's own `next` text.
- A request to set, change or move the marketplace of a plugin ("change the marketplace association") goes after the language gate directly to `flows/associate.md`; it needs the configuration evidence of the kind `plugin`. A plugin belongs to exactly one marketplace (R21): the status answer reports `association` (`marketplace`, `path`, `state`) as a read-only hint for a plugin, never as a gate for `ready`; a missing local path (`path_missing`, for example on a fresh clone) is only mentioned when installation, publication or association is asked for.
- Files this entry manages in the workpackage: `.project/plugins/plugin-manager/config.json` (configuration evidence, schema_version 2 with the mandatory `marketplace` identity of a plugin; written by `record` and, when the marketplace changes, by `associate`), `.project/plugins/plugin-manager/local.json` (Git-ignored path of the one marketplace checkout; written only by the plugin generator and `associate`) and `.project/plugins/plugin-manager/skeleton.json` (skeleton evidence, schema_version 2); the plugin skeleton is the `common` list of `../_shared/manifests/plugin.json`, the marketplace skeleton that of `../_shared/manifests/marketplace.json`.
- Configuration uses the existing `create --kind plugin` generator with its documented prerequisites (it reads Git metadata); the entry adds no Git mutation or network action. This does not alter docs, verify, publish or `create --kind plugin`.
- On `ready` output only the ready line `Plugin <name> Status: fully configured` (German `Plugin <name> Status: vollständig konfiguriert`; `<name>` is the field `plugin` of the status answer, the configured repository) with no remark, exactly once and without a closing-summary or next-step card, and wait.
