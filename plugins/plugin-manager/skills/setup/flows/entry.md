# setup (state loop)

`<plugin>` is the name of the running plugin (`plugin-manager`) and is passed to every helper call as `--plugin`. This file, `language.md`, `skeleton.md`, `sync.md` and the helper `../scripts/setup_state.py` belong to the skill `setup` (`../../setup/SKILL.md`, `../../setup/flows/configure.md`).

Specialised actions stay in their own skills. Helper: `../scripts/setup_state.py`; language rules: `../../_shared/references/operator-language.md`, which applies only where it does not conflict with this entry. Precedence: this entry's read-only rule and flow order win. In particular its direct `--set` before continuing and its rule to ask/save a missing language even for read-only actions do not apply here. The reference still governs the tag format, never guessing a language, reuse of the saved language and independence of content languages. Resolve paths from this loaded file; never search host caches.

## Loop

1. Determine the explicitly selected folder (user input or current project). Ask only which one if several are possible. Never the installed plugin directory or unrelated projects.
2. Run `python3 -B "<helper>" status --target "<folder>" --plugin <plugin>` (JSON, writes nothing, needs no Git, origin or marketplace; `--plugin` is the name of this running plugin and is passed to every helper call below). Configuration of the workpackage for this plugin is proven only by `.project/plugins/<plugin>/config.json`; a root plugin.json or marketplace.json is a product, never evidence. Read `next`:

| `next` | Meaning | Action |
| --- | --- | --- |
| `stop` (`state: conflict`, exit 1) | technical conflict | Explain what is wrong with which folder or file in plain words (see `../../_shared/references/messages.md`), change nothing, wait. Other project content is named, never adopted. |
| `language` | operator language missing | follow `language.md` |
| `configure` | no valid configuration evidence of this plugin in the workpackage | follow `../../setup/flows/configure.md` (the plugin's own configuration dialogue) |
| `skeleton` | skeleton files of the configured kind, ignore rule or skeleton evidence missing | follow `skeleton.md` |
| `sync` | a managed file differs from the template, or its source was removed and its local file is changed or accepted, and needs a decision | follow `sync.md` |
| `ready` | configured and in sync, no automatic flow open | output exactly one line and wait (see below) |

3. Success is judged per flow, because the answers differ. `language`, `setup`, `sync` and `record`: exit 0 and `ok: true` (with `next: "status"`). Configuration is the plugin's own flow and ends with `record`, which writes the configuration evidence only after that flow succeeded by its own success criterion; the flow names that criterion. After each flow that succeeded in this sense, run `status` again and decide from the new answer; never jump to the next step by assumption.
4. Stop and report instead of repeating when a flow fails (`language`/`setup`/`sync`: `ok: false` or exit 1; configuration: the failure criterion of its own flow, the cause, what was already changed and the next step) in the plain words of `../../_shared/references/messages.md` (never exit codes, field names or raw error text; do not repeat "nothing was changed" from a status check), when the person has not answered or an external prerequisite that no answer can fix is missing (state it once and wait; a missing answer or selection is first asked for in the guided dialogue of the flow, do not ask again in a loop); a cancelled or unanswered question is such a pause: respect it, do not ask again until the entry is called again, or when a flow claimed success but the next `status` shows the same `next` without progress (report the cause, do not retry).
5. Binding: read and apply `../../_shared/references/messages.md` for every failure, stop and result you report, and `../../_shared/references/operator-language.md`, in particular its section "Language of all visible text", for every visible text you write (reports, questions, choice labels, closing or next-step card fields). The rules of this entry stay as stated here: read-only asks and saves no language (see below), the setup order with the ignore rule, on `ready` output only the ready line and wait; start no verify or other action on your own, and the success and failure rules of the flows apply unchanged.
6. Never show, quote or describe the content of a managed file or of a difference: no excerpts, diffs or content summaries, not in questions, not in the final report, not for `ready`, not for accepted deviations or kept files. Name only the path and the fact (differences exist, deviation accepted, source removed, file kept or removed). Never say the project matches the template unless `matches_template` is true. `ready` is not product acceptance: it only means the workpackage is configured for this plugin and no automatic setup flow is open. A configuration failure already reported in this conversation stays an open, named problem; because the evidence is written only after a passed run, it cannot be shown as `ready` by that run. A deviating managed file is never overwritten automatically: it needs the person's explicit decision (`sync.md`). Only an explicit `adopt` takes over the template content; `keep` makes it an `accepted` deviation (a deliberately accepted difference), which is listed but neither re-asked nor reported as matching the template, so there is no endless re-sync.

## Ready output

On `ready` write exactly one line in the operator language and nothing else (no greeting, no list of skeleton deviations unless the person asks): English `Plugin <plugin> Status: fully configured`, German `Plugin <plugin> Status: vollständig konfiguriert`; for another language translate only the status words. Then wait for input.

## Read-only requests

If the request is concretely read-only (for example "check", "status", "what is missing"), run exactly one `status`: ask nothing, save nothing, start no flow, and report the result with language need, skeleton need and configuration need kept separate.

## Status answer

`{"ok", "state": "<kind>"|"unconfigured"|"conflict" (the configured kind, from the evidence), "plugin_configured", "configuration": {"plugin", "configured", "kind"}, "next": "stop"|"language"|"configure"|"skeleton"|"sync"|"ready", "language": {"operator_language", "needs_choice"}, "skeleton": {"open", "missing_files", "lock_pending", "ignore_rule_pending", "different", "accepted_deviations"}, "removals": {"auto", "decisions", "kept", "unowned", "lock_cleanup"}, "sync": {"needed", "decisions": [{"path", "reason", "source_hash", "local_hash", "accepted", "source_changed", "local_changed", "source_file", "local_file"}]}, "files", "conflicts", ...}`. `files` states: `missing`, `identical`, `accepted` (differs, but the stored source/local pair still fits), `decision_needed`, and for managed paths whose source was removed in the parent: `removed` (local absent), `auto_remove`, `removal_decision`, `removal_kept` (stored `source_hash` null, local unchanged), `unowned` (no lock evidence, never touched). `removals` lists these separately; `removals.auto` and `removals.lock_cleanup` are executed by the skeleton flow (`next: skeleton`), `removals.decisions` by the sync flow. Priority is fixed: conflict, language, configuration, skeleton, sync, ready. The former `.project/plugin.skeleton.lock.json` is an unsupported location: it is a conflict and is neither read, migrated nor deleted.

## Boundaries

The skeleton is the `common` list of the configured kind's manifest (`../../_shared/manifests/<kind>.json`) plus parent folders, the ignore rule and the skeleton evidence; it contains no plugin.json or placeholder identity. Deletion is limited to a managed file whose source was removed in the parent template and for which the lock proves ownership: it is removed automatically only if the current local hash equals the stored `local_hash` and the stored `source_hash` (untouched since it matched the template); a changed or deliberately accepted local file is always asked (keep or delete), and without lock evidence nothing is ever deleted. Locally already missing owned files only lose their lock entry. After a removal only the empty parent folders of the removed file go, bottom-up with `rmdir`, and never folders still needed, the project root, `.git`, `.idea` or `.project`; foreign files are never deleted and no folder is hashed, moved or removed recursively. Extra local files stay. An existing managed file is replaced only by an explicit `adopt` decision of the person for the shown source/local pair (`sync.md`); `keep`, the skeleton flow and every other flow never replace its bytes. Removal is a separate act with its own rules: only the automatic removal and the explicit `delete` decision described here delete a file. The other existing files the helper may modify are `.gitignore` (exact rule line added), `.project/operator.json` (language, written only when none is stored), `.project/plugins/<plugin>/config.json` (configuration evidence, written once by `record` after a passed configuration run) and `.project/plugins/<plugin>/skeleton.json` (schema_version 2, hash pairs per path, merged in; an older or invalid file is rejected unchanged, never migrated). `status`, `language` and `setup` never open `.git` or `.idea` (they only verify real directories) and need no Git, origin or marketplace. This entry adds no Git mutation or network action, installs nothing and executes no target code. Skill text does not prove host or model behavior; activation by a slash command is untested.
