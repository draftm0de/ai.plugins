# Flow: configuration (plugin or marketplace)

Used when `status` says `next: configure` (the language is known; this plugin has no configuration evidence in the workpackage). Stay in this call and in this folder; do not send the person to another command or folder.

0. Ask first, alone and explicitly (host question tool, labels in the operator language, no preselection): "Plugin or marketplace?". The answer is the `kind`. A root plugin.json or marketplace.json that already exists is only named as a fact (path), never taken as the answer or as evidence. *Plugin* with an already existing root plugin.json: name the path and stop; taking over an existing plugin repository is not part of this flow, and the generator would refuse it. The one exception is the recovery of step 7: the person confirms explicitly that this plugin.json comes from an earlier run of this flow that stopped at `record`. *Marketplace* continues with `flows/marketplace.md` (it uses the dialogue rules of the section "Guided dialogue (both kinds)" below and ends with `record --kind marketplace`), *plugin* with the steps below. Nothing is written for the configuration before step 4.

1. Follow `../../_shared/references/workflows.md` for the required inputs, the licensing decision and the `create --kind plugin --skeleton` helper call with `--root "<folder>"`. The operator language counts as the established conversation language (do not ask it again). This flow runs only when no valid configuration evidence of this plugin exists.
2. Required facts (never invent or dummy-fill them): technical and display name, description, publisher, documentation languages, license decision (or explicit deferral), the GitHub origin of the checkout and the **explicitly selected** marketplace checkout, the one marketplace the plugin belongs to (R21: its identity goes into the committed `config.json`, the path of the checkout into the Git-ignored `local.json`). Never change another marketplace without that selection; changing the marketplace later is the request `flows/associate.md` handles. Ask them with the guided dialogue below.
   - Marketplace: a suggestion is never a selection. Even with a single candidate ask for explicit confirmation of the concrete path as a real decision ("Use this checkout" / "Choose another checkout"); never add a filler option, and never adopt a candidate because of a suggestion, a preselection or a tool error. For another checkout ask for the path with one targeted question and confirm it. A path the person already confirmed explicitly in this conversation is not asked again.
3. A missing external prerequisite that no answer can fix (for example no Git checkout with a GitHub `origin`) is named once, keeping everything already created (language, skeleton evidence, `.git`, `.idea`); then wait. This rule never replaces asking for a missing selection or fact in step 2, and it is not a failure of the skeleton; never roll anything back, create or set remotes or repositories, or publish.
4. Run the generator only after all required facts are answered and the marketplace checkout is explicitly confirmed. Until then nothing is written for the configuration.
5. The generator never judges or replaces an existing synced skeleton file (also a deviating one or one the person deliberately kept in the sync flow): nothing is replaced and it does not fail because of such a file. Deviations are only resolved by the sync flow once the configuration evidence exists.
6. Judge the result by the generator's own answer, which has `action`, `changed`, `checks` and a prose `next` but no `ok`: success means exit 0 **and** `checks.status == "passed"` (`checks.licensing` shows whether the license is implemented, deferred or inconsistent). On a non-zero exit or `needs_attention`, report the failure in the plain words of `../../_shared/references/messages.md` (what is wrong with which folder or file, what was already created, what to do next; never the answer's field names, exit codes or raw error text), and stop; do not say "ready", do not derive success from a plugin.json that now exists, and do not run `status` to declare it done. A `ready` from a later `status` stays only "no automatic setup flow open" while this problem is unresolved.
7. Only after a passed run write the evidence: `python3 -B "<helper>" record --target "<folder>" --plugin plugin-manager --kind plugin|marketplace --artifact <name>`. `record` checks that the root plugin.json (or marketplace.json) exists with exactly that name and writes `.project/plugins/plugin-manager/config.json` (schema_version 2). For the kind plugin it derives the identity `marketplace: {name}` itself from the path in `local.json` that the generator wrote and requires the catalog entry of the plugin there; without a valid association it refuses with `association_missing` ("associate first") and writes nothing; after such a refusal, or any other failure of `record`, the generator has already succeeded and the product exists, so do not run the generator again: report the cause, let the person fix it (for example a marketplace.json without `repository`), then run `record` again with the artifact named in plugin.json (a run that stopped at `record` is resumed this way and nothing else); judge it by exit 0 and `ok: true`, on failure report `conflicts`/`errors` and stop. The skeleton files of the chosen kind then come from the skeleton flow. Then run `status` again (see SKILL.md); then report open decisions (for example a deferred license) and pending domain implementation. Do not publish, install or implement anything.

## Guided dialogue (both kinds)

These rules apply to the plugin steps above and to `flows/marketplace.md`.

- Guided dialogue, identical on the first call, after an aborted dialogue, after every answer and after a tool error: every call of this entry re-reads `status` and this flow and applies it from the start. Do not summarize all open facts as a text list, do not offer a free-text "write me the details" form and do not ask which dialogue form the person prefers.
- Take over only facts the person explicitly answered in the current conversation. A question that was cancelled, dismissed, rejected by the host or left unanswered is not an answer and stays open. Answers given so far live only in the chat: no new persistence and no configuration write before step 4.
- Ask the next open question, or one small coherent group, with the host's question tool (for example `AskUserQuestion` with its actual schema and limits). Without such a tool, or for free facts without a meaningful choice (name, description, rights holder, paths), ask exactly one targeted text question per message and wait.
- A schema error or rejection of a question call means that no question in it was answered. Ask the valid questions again, separately and correctly formed; the duty of an explicit selection stays, whatever the generic tool error says.
- Only an explicit request of the person for a complete list or a text mode may change this form.
- Missing choices are asked first, one step at a time; only after a deliberate postponement or cancellation by the person respect it: state briefly that configuration is paused, keep everything already created, and wait. Do not ask again on your own; the next call of this entry continues with the next open question.

## Creation rules retained by this internal flow

The internal `create --kind plugin --skeleton` Python operation creates only a nonfunctional scaffold. Never offer skill import, a source skill path or a creation mode. Reuse confirmed facts; never invent domain capabilities or license terms. Documentation languages are independent of the saved operator language. Do not present CLI flags as required user input.

Before generator writes, resolve the license explicitly: reuse an unambiguous existing license or session decision, otherwise ask for a license or explicit deferral and wait. Silence is not deferral. Preserve existing license bytes and clarify conflicts. For MIT, confirm copyright year and rights holder (publisher is not automatically rights holder); pass `--license MIT`, `--copyright-year` and `--copyright-holder`. For another license, use a confirmed identifier and complete `--license-file`. Use `--license deferred` only after explicit deferral, and report it as unresolved. Check `checks.licensing` against the files actually created.

Preserve existing prose and resolve reported documentation gaps within the creation request. Separate structural checks, documentation, licensing, pending domain implementation and tests/host checks actually run in the report. A `needs_attention` result is incomplete creation, not success. Never execute target code as part of these checks.
